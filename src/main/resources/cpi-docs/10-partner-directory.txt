Partner Directory in SAP CPI
Source: SAP Help Portal - Partner Directory

The Partner Directory is a central repository in SAP CPI for storing partner-specific configuration data. It enables you to build multi-partner integration flows that dynamically adapt behavior based on the trading partner involved.

Why Partner Directory:
Without Partner Directory, you would need separate iFlows (or complex branching) for each partner. With Partner Directory, a single iFlow can handle hundreds of partners by looking up partner-specific settings at runtime.

Partner Directory Components:

1. Partner:
A partner entry represents a trading partner (supplier, customer, etc.).
- PID (Partner ID): unique identifier, typically a business ID (GLN, DUNS, SAP Vendor Number)
- Each partner can have multiple parameters, binary parameters, and alternative partner entries

2. String Parameters:
Key-value pairs that store partner-specific configuration as text.
Examples:
- AS2 endpoint URL
- Target folder path for SFTP
- EDI version (D.96A, D.01B)
- IDoc message type
- Receiver system ID
- Custom processing flags

3. Binary Parameters:
Partner-specific binary data, typically certificates or keys.
Examples:
- Partner's public certificate for AS2 encryption
- Partner's signing certificate for signature verification
- Custom schema files

4. Alternative Partners:
Mappings between different identification systems for the same partner.
Example: Partner "ACME Corp" might be known as:
- GLN: 1234567890123
- DUNS: 987654321
- SAP Vendor: 0001000100
- AS2 ID: ACME-AS2

The Alternative Partner lookup allows CPI to find the correct partner regardless of which ID system the inbound message uses.

5. Authorized Users:
Users (typically certificate subjects or technical users) authorized to send messages on behalf of a specific partner. Used for sender authentication in inbound scenarios.

Using Partner Directory in iFlows:

Method 1: Script-Based Lookup
import com.sap.it.api.pd.PartnerDirectoryService
import com.sap.it.api.ITApiFactory

def Message processData(Message message) {
    def service = ITApiFactory.getService(PartnerDirectoryService.class, null)

    def partnerId = message.getHeaders().get("AS2-From")

    // Lookup string parameter
    def targetUrl = service.getStringParameter("TargetEndpoint", partnerId)
    def ediVersion = service.getStringParameter("EDIVersion", partnerId)

    // Lookup binary parameter (e.g., certificate)
    def certBytes = service.getBinaryParameter("PartnerCert", partnerId)

    // Lookup alternative partner
    def sapVendorId = service.getAlternativePartner("SAP_VENDOR", partnerId)

    message.setProperty("targetUrl", targetUrl)
    message.setProperty("ediVersion", ediVersion)

    return message
}

Method 2: Dynamic Configuration via Headers
Use CPI dynamic parameters to reference Partner Directory:
- pd:partnerId:parameterName — in adapter or Content Modifier expressions

Populating Partner Directory:

Via OData API:
CPI exposes an OData API for managing Partner Directory entries programmatically:
- POST /api/v1/StringParameters — create string parameter
- POST /api/v1/BinaryParameters — create binary parameter
- POST /api/v1/AlternativePartners — create alternative partner mapping
- GET, PUT, DELETE operations also supported

Via Integration Flow:
You can build an iFlow that reads partner data from a source (Excel, database, SAP MDG) and populates the Partner Directory via the OData API. This enables automated partner onboarding.

Partner Directory Design Patterns:

Pattern 1: Dynamic Routing
Look up the partner's endpoint URL and protocol from Partner Directory to route messages to the correct destination without hardcoding.

Pattern 2: Dynamic Mapping
Look up the partner's preferred document format or version and apply the correct mapping template.

Pattern 3: Partner Onboarding Automation
Build an onboarding iFlow that:
1. Receives new partner data (from a form, email, or master data system)
2. Creates Partner Directory entries
3. Exchanges certificates
4. Sends a test message
5. Activates the partner

Pattern 4: Multi-Standard B2B Hub
A single iFlow acts as a B2B hub:
1. Receive message from any partner
2. Identify partner from message headers
3. Look up partner's inbound format (EDIFACT, X12, cXML)
4. Convert to internal format
5. Process and route
6. Look up target partner's outbound format
7. Convert and send

Best Practices:
1. Use meaningful, stable IDs for partners (GLN, DUNS) rather than internal sequence numbers.
2. Use Alternative Partners to support multiple ID systems per partner.
3. Store certificates in Binary Parameters rather than in the tenant Keystore — this keeps partner certs separate from system certs.
4. Use descriptive parameter names (e.g., "AS2_Endpoint_URL" not "param1").
5. Build automation for partner onboarding — manual Partner Directory maintenance does not scale.
6. Regularly audit Partner Directory entries for outdated or inactive partners.
7. Use Authorized Users for strict sender authentication in production scenarios.
8. Version your Partner Directory configuration alongside your iFlows.
