Error Handling in SAP CPI Integration Flows
Source: SAP Help Portal - Error Handling, SAP Community

Proper error handling is critical for building reliable integration flows in SAP CPI. Without it, messages can fail silently or produce unclear errors that are hard to debug.

Error Handling Mechanisms:

1. Exception Subprocess
The Exception Subprocess is the primary error handling mechanism in CPI. It catches exceptions thrown during message processing and allows you to define custom error handling logic.

How to add an Exception Subprocess:
- In the iFlow editor, right-click on the Integration Process pool
- Select "Add Exception Subprocess"
- An Exception Subprocess appears as a separate pool within the integration process
- Add steps inside it to handle the error (e.g., send error notification, log error details)

The Exception Subprocess:
- Catches ALL unhandled exceptions in the main integration process
- Has access to the exception details via headers:
  - SAP_ErrorHeader: contains the error message
  - CamelExceptionCaught: contains the full Java exception object
- Can modify the message body to create a custom error response
- Can send the error to an external system (email, error queue, monitoring tool)

Example — Error notification script in Exception Subprocess:
import com.sap.gateway.ip.core.customdev.util.Message

def Message processData(Message message) {
    def ex = message.getHeaders().get("CamelExceptionCaught")
    def errorMessage = ex?.getMessage() ?: "Unknown error"
    def messageId = message.getHeaders().get("SAP_MessageProcessingLogID")

    def errorBody = """
    {
        "error": true,
        "messageId": "${messageId}",
        "errorMessage": "${errorMessage}",
        "timestamp": "${new Date().format('yyyy-MM-dd HH:mm:ss')}"
    }
    """

    message.setBody(errorBody)
    message.setHeader("Content-Type", "application/json")
    return message
}

2. Error End Event
An Error End Event can be placed at the end of a route or subprocess to explicitly trigger an error. When reached, it stops processing and marks the message as failed.

Use cases:
- After a validation check fails
- When a business rule is violated
- To explicitly fail a message with a custom error message

3. Escalation End Event
An Escalation End Event ends a subprocess and passes control back to the main process. Unlike Error End Event, it does not mark the message as failed. It allows the main process to continue with different logic.

4. Try-Catch in Scripts
Within Groovy scripts, use standard try-catch blocks for fine-grained error handling:

def Message processData(Message message) {
    try {
        def body = message.getBody(String)
        // risky operation
        def parsed = new groovy.json.JsonSlurper().parseText(body)
        message.setProperty("parsedData", parsed)
    } catch (Exception e) {
        message.setProperty("scriptError", e.getMessage())
        message.setHeader("X-Error", "true")
        // Don't re-throw if you want processing to continue
        // throw e  // Uncomment to escalate to Exception Subprocess
    }
    return message
}

5. Adapter-Level Error Handling
Many adapters have built-in error handling options:
- Retry Configuration: automatic retries with configurable intervals
- Dead Letter Queue: failed messages are routed to a separate queue
- On Error: "Stop Processing" or "Continue Processing"

6. Router-Based Error Handling
Use a Router step after an operation to check for error conditions:
- Route based on headers (e.g., HTTP response code)
- Route based on properties set during processing
- Default route for unexpected conditions

Error Classification in CPI Monitoring:

Messages in CPI monitoring can have these statuses:
- Completed: Successfully processed
- Failed: An unhandled error occurred
- Retry: Scheduled for automatic retry
- Escalated: Manual intervention required
- Cancelled: Processing was cancelled
- Discarded: Message was intentionally discarded

Retry Handling:
CPI supports automatic retry for failed messages:
- JMS queues provide built-in retry with configurable retry intervals
- The retry count and interval are configurable per channel
- After max retries, messages move to a dead letter queue or are marked as failed
- XI adapter and AS2 adapter support retry natively

Custom Retry Logic:
For adapters without built-in retry, you can implement custom retry:
1. Use a Looping Process Call with a counter
2. Set a retry counter as an exchange property
3. On failure, increment counter and loop
4. On success or max retries reached, exit loop

Error Handling Patterns:

Pattern 1: Catch-and-Notify
- Exception Subprocess catches the error
- Sends an email or posts to a monitoring system
- Message status: Failed (with notification sent)

Pattern 2: Catch-and-Retry
- Exception Subprocess catches the error
- Stores the message in a data store
- A separate iFlow picks up failed messages and reprocesses them

Pattern 3: Catch-and-Transform
- Exception Subprocess catches the error
- Transforms the error into a business-level response
- Sends the error response back to the caller
- Message status: Completed (caller gets error info)

Pattern 4: Graceful Degradation
- Use Router to check operation results
- If primary path fails, try alternative path
- Log the degradation for monitoring

Best Practices:
1. Always add an Exception Subprocess to production iFlows — never let errors go unhandled.
2. Log error details (message ID, error message, timestamp) for troubleshooting.
3. Use meaningful error messages that help identify the root cause.
4. Set appropriate retry configurations for transient errors (network timeouts, temporary unavailability).
5. Do NOT retry on permanent errors (invalid data, authentication failures).
6. Use Custom Header Properties to pass error context between steps.
7. Test error scenarios explicitly — don't just test the happy path.
8. Consider using the Data Store for persisting failed messages for later reprocessing.
9. Set up alerts in CPI monitoring for critical integration flows.
10. Document your error handling strategy for each integration flow.
