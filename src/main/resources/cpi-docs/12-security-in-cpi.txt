Security in SAP CPI
Source: SAP Help Portal - Security, Managing Security Material

Security is a critical aspect of SAP CPI, especially for B2B scenarios where sensitive business documents are exchanged between organizations.

Security Layers:

1. Transport-Level Security (TLS/HTTPS):
- All communication should use HTTPS
- CPI tenant endpoints are HTTPS by default
- TLS 1.2 or higher is required
- Certificate-based server authentication

2. Message-Level Security:
- Encryption: protects message content
- Digital Signature: ensures message integrity and authenticity
- Applied within the message itself (survives intermediaries)
- Standards: PKCS#7/CMS, XML Signature, WS-Security, PGP

3. Authentication:
- Verifies the identity of the communicating party
- Methods: Basic Auth, Client Certificate, OAuth 2.0, SAML

4. Authorization:
- Controls what authenticated users/systems can do
- Role-based access in CPI
- Sender authorization in Partner Directory

Security Material Management:

Keystore:
The CPI Keystore stores certificates and key pairs.
- Location: Operations -> Manage Security -> Keystore
- Contents:
  - Key Pairs: private key + certificate (for signing, decryption, TLS client auth)
  - Certificates: public certificates of partners and CAs
  - Certificate Chains: intermediate and root CA certificates

Key Pair Operations:
- Generate: create a new key pair and CSR (Certificate Signing Request)
- Import: upload a key pair (PKCS#12/PFX format)
- Renew: update a certificate while keeping the same key
- Download: export the public certificate for sharing with partners

User Credentials:
Store username/password pairs for adapter authentication.
- Location: Operations -> Manage Security -> User Credentials
- Referenced by alias in adapter configurations
- Passwords are encrypted at rest

Secure Parameters:
Store encrypted key-value pairs for use in scripts.
- Access in Groovy: def secureParam = ITApiFactory.getService(SecureStoreService.class, null).getUserCredential("alias")
- Use for API keys, tokens, or other secrets

OAuth2 Credentials:
Store OAuth 2.0 client configuration.
- Client ID and Secret
- Token endpoint URL
- Scope
- CPI handles token refresh automatically

Message-Level Security Steps:

PKCS#7/CMS Encryptor:
- Encrypts the message body using partner's public certificate
- Algorithms: AES-128, AES-256, 3DES
- Output: binary PKCS#7 envelope

PKCS#7/CMS Decryptor:
- Decrypts PKCS#7 encrypted messages
- Uses your private key from the Keystore

PKCS#7/CMS Signer:
- Signs the message body using your private key
- Creates a digital signature proving authenticity and integrity
- Algorithms: SHA-256, SHA-384, SHA-512

PKCS#7/CMS Verifier:
- Verifies the digital signature on an incoming message
- Uses the sender's public certificate

PGP Encryptor/Decryptor:
- PGP (Pretty Good Privacy) encryption/decryption
- Common in B2B file-based exchanges
- Supports PGP public/secret key rings
- Import PGP keys via Security Material

XML Digital Signature:
- Signs XML documents according to W3C XML Signature standard
- Supports enveloped, enveloping, and detached signatures
- Used in SOAP WS-Security scenarios

Certificate Management Best Practices:

Certificate Lifecycle:
1. Generate or obtain certificates well before go-live
2. Exchange public certificates with all trading partners
3. Monitor certificate expiry dates (set reminders 30-60 days before)
4. Renew certificates before they expire
5. Distribute renewed certificates to all affected partners
6. Update CPI Keystore with renewed certificates
7. Verify communication after certificate renewal

Common Certificate Issues:
- Expired certificate: communication fails with SSL/TLS handshake error
- Wrong certificate: signature verification or decryption fails
- Missing intermediate CA: certificate chain incomplete, trust not established
- Self-signed certificates: must be explicitly trusted by both parties

Security for B2B Scenarios:

AS2 Security:
- Message signing: PKCS#7/CMS signature
- Message encryption: PKCS#7/CMS encryption
- MDN signing: ensures non-repudiation of receipt
- Certificate-based partner authentication

SFTP Security:
- Key-based authentication (SSH keys)
- Known Hosts verification (prevent MITM attacks)
- File-level encryption (PGP) on top of transport encryption

EDI Security:
- Transport: AS2 (signed + encrypted) or SFTP (encrypted channel)
- Application: EDI content itself is typically not encrypted (relies on transport)
- Authentication: partner identification via ISA/UNB sender/receiver IDs + AS2 IDs

Best Practices:
1. Use certificate-based authentication over Basic Auth wherever possible.
2. Rotate credentials and certificates regularly.
3. Use separate key pairs for signing and encryption.
4. Monitor certificate expiry proactively.
5. Never share private keys — only exchange public certificates.
6. Use AES-256 for encryption and SHA-256+ for signing.
7. Enable audit logging for security-related operations.
8. Restrict access to Security Material operations to authorized administrators.
9. Test certificate renewal procedures before they become urgent.
10. Document all security configurations and certificate exchange records.
