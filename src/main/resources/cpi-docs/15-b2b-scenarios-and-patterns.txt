Common B2B Integration Scenarios and Patterns in SAP CPI
Source: SAP Help Portal, SAP Community Best Practices

This document describes real-world B2B integration scenarios and design patterns commonly implemented in SAP CPI.

Scenario 1: Purchase Order Processing (Inbound from Partner)

Flow: Partner -> AS2/SFTP -> CPI -> SAP S/4HANA

Steps:
1. Partner sends an EDI 850 (X12) or ORDERS (EDIFACT) purchase order
2. CPI receives via AS2 sender adapter
3. EDI Splitter separates individual orders from a batch interchange
4. EDI Validator checks structure and mandatory fields
5. EDI-to-XML Converter transforms to XML
6. Message Mapping converts EDI XML to SAP IDoc (ORDERS05)
7. Partner Directory lookup for partner-specific mapping rules
8. IDoc receiver adapter sends to SAP S/4HANA
9. Acknowledgment (997/CONTRL) is generated and sent back to partner

Error handling:
- Validation failures: generate a negative acknowledgment with error details
- Mapping errors: store failed message in data store for manual review
- SAP unavailable: JMS queue holds messages for retry

Scenario 2: Invoice Sending (Outbound to Partner)

Flow: SAP S/4HANA -> CPI -> AS2/SFTP -> Partner

Steps:
1. SAP S/4HANA creates a billing document and generates IDoc (INVOIC02)
2. IDoc sender adapter in CPI picks up the IDoc
3. Message Mapping converts IDoc to EDI XML structure
4. Partner Directory lookup: determine partner's EDI version and format preference
5. XML-to-EDI Converter creates the EDI message (810/INVOIC)
6. EDI envelope: add interchange and group headers with correct control numbers
7. AS2 receiver adapter sends signed and encrypted message to partner
8. MDN received and logged

Scenario 3: Advance Ship Notice / Despatch Advice

Flow: Warehouse/3PL -> SFTP -> CPI -> Partner (Retailer)

Steps:
1. Warehouse management system generates shipping data as CSV/XML file
2. CPI polls SFTP server for new files
3. File content is parsed and transformed
4. Mapping to EDI 856 (ASN) or DESADV format
5. Partner-specific adjustments from Partner Directory
6. Send to retailer via AS2
7. Track acknowledgment

This is critical in retail B2B — many retailers (Walmart, Amazon, Target) require ASN within hours of shipment and penalize (chargeback) for late or missing ASNs.

Scenario 4: PunchOut Catalog with Ariba

Flow: Ariba Network <-> CPI <-> Supplier Commerce Platform

Detailed flow:
1. Buyer in Ariba clicks "Browse Supplier Catalog"
2. Ariba sends cXML PunchOutSetupRequest to CPI endpoint
3. CPI authenticates request (SharedSecret), routes to supplier
4. Supplier returns PunchOutSetupResponse with catalog URL
5. CPI relays response to Ariba
6. Buyer browses catalog in embedded browser
7. Buyer adds items to cart and checks out
8. Supplier sends cXML PunchOutOrderMessage to CPI
9. CPI maps and forwards to Ariba
10. Cart items appear in Ariba requisition
11. After approval, Ariba sends cXML OrderRequest via CPI to supplier
12. Supplier processes order and sends ConfirmationRequest via CPI

Scenario 5: Multi-Partner B2B Hub

A centralized integration hub that routes documents between multiple partners.

Architecture:
                    Partner A (EDIFACT)
                   /
SAP S/4HANA <-> CPI Hub <-> Partner B (X12)
                   \
                    Partner C (cXML)

Design:
1. Single inbound iFlow with AS2/SFTP sender adapters
2. Partner identification step (from AS2-From header, certificate, or file naming)
3. Partner Directory lookup for format, version, and routing
4. Dynamic format detection and conversion
5. Single mapping template with partner-specific overrides
6. Dynamic routing to backend systems
7. Single outbound iFlow with dynamic adapter selection

Benefits:
- Fewer iFlows to maintain
- Centralized partner management
- Consistent monitoring and error handling
- Easy to onboard new partners

Scenario 6: VAN Replacement

Many companies are replacing Value-Added Networks (VANs) with direct AS2 connections via CPI.

VAN Traditional Flow:
Company -> VAN -> Partner
(Monthly VAN fees, per-transaction charges, limited visibility)

Direct CPI Flow:
Company -> CPI -> AS2 -> Partner
(No VAN fees, real-time delivery, full monitoring)

Migration approach:
1. Set up AS2 connectivity with each partner in CPI
2. Run parallel with VAN during transition
3. Compare results to ensure parity
4. Switch partners one by one from VAN to direct

B2B Design Patterns:

Pattern: Store-and-Forward
Use JMS queues or data stores to decouple inbound receipt from outbound delivery.
Benefits: sender gets immediate acknowledgment, processing continues asynchronously, natural retry mechanism.

Pattern: Canonical Format
Convert all partner formats to a single internal (canonical) format, process in canonical, then convert to each partner's outbound format.
Benefits: N partner formats become N inbound converters + 1 canonical processor + N outbound converters, instead of N*N point-to-point mappings.

Pattern: Correlation and Aggregation
Track related documents across a business process:
PO -> PO Acknowledgment -> Ship Notice -> Invoice -> Payment
Use data store to maintain the state of each business transaction.

Pattern: Throttling and Rate Limiting
Some partners or backend systems have throughput limits. Use:
- JMS queues with controlled consumption rate
- Timer-based processing with batch sizes
- Sequential processing with configurable delays

Pattern: Fallback Communication
If primary channel (AS2) fails, automatically switch to backup (SFTP).
Implement with Router checking communication result and a retry path.

Compliance and Audit:

B2B integrations often require:
1. Non-repudiation: signed messages and MDN prove delivery
2. Audit trail: log all messages with timestamps, partner IDs, and document IDs
3. Archival: store raw EDI/cXML messages for regulatory compliance (often 7+ years)
4. SLA monitoring: track processing times and delivery success rates
5. Chargeback prevention: timely and accurate ASN/invoice delivery to avoid retailer penalties

Best Practices for B2B in CPI:
1. Design for multi-partner from the start — even if you start with one partner.
2. Use Partner Directory extensively for partner-specific configuration.
3. Implement comprehensive monitoring and alerting for B2B flows.
4. Always generate and track acknowledgments.
5. Plan for certificate lifecycle management across all partners.
6. Document partner agreements (formats, schedules, SLAs) outside of CPI.
7. Test with each partner individually before go-live.
8. Keep raw messages for compliance — use data store or external archival.
9. Build automated partner onboarding to scale beyond a handful of partners.
10. Monitor EDI control number sequences to detect gaps or duplicates.
