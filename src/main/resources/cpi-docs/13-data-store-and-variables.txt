Data Store and Variables in SAP CPI
Source: SAP Help Portal - Data Store, Variables

SAP CPI provides several mechanisms for storing data temporarily or persistently during and between message processing runs.

Data Store:
The Data Store is a persistent storage within CPI that allows you to store, retrieve, and delete messages. It survives iFlow restarts and can be accessed across different iFlows on the same tenant.

Data Store Operations:

Write (Store):
- Stores a message entry in a named data store
- Each entry has a unique Entry ID (auto-generated or custom)
- Configuration:
  - Data Store Name: logical name of the store
  - Visibility: Global (accessible from all iFlows) or Integration Flow (only this iFlow)
  - Entry ID: unique key for the entry
  - Retention Threshold (days): auto-delete after N days
  - Overwrite Existing: whether to replace if Entry ID exists

Get (Retrieve):
- Retrieves a single entry by Data Store Name + Entry ID
- Options:
  - Delete On Completion: remove the entry after successful retrieval

Select (Query):
- Retrieves multiple entries from a data store
- Filter by: number of entries (top N), overdue entries
- Returns entries as a multimap (XML with multiple entries)

Delete:
- Removes a specific entry by Data Store Name + Entry ID

Data Store Use Cases:

1. Message Persistence for Retry:
Store failed messages in a data store. A separate timer-triggered iFlow periodically retrieves and reprocesses them.

2. Duplicate Detection:
Before processing a message, check if its ID already exists in the data store. If yes, skip (deduplicate). If no, store the ID and process.

3. Collect and Merge:
Store individual messages as they arrive. When all expected messages are received, retrieve all and merge into a single message.

4. Cross-iFlow Communication:
iFlow A stores data in a global data store. iFlow B retrieves and processes it. This enables asynchronous decoupling.

5. Audit Trail:
Store key message data (IDs, timestamps, status) for audit purposes.

Data Store in Monitoring:
- View data store contents: Operations -> Manage Stores -> Data Stores
- See all entries, their IDs, creation dates, and expiry
- Manually delete entries
- Download entry content

Variables:
Variables in CPI are simpler than Data Stores — they store single values (not full messages) that persist across message processing runs.

Variable Operations:

Write Variable:
- Store a single value with a name
- Visibility: Global or Integration Flow
- Value can be set from header, property, or expression

Read Variable:
- Retrieve a variable value into a header or property

Variable Use Cases:
1. Timestamp tracking: store the last successful run timestamp for delta processing
2. Counter/sequence: maintain a running counter across iFlow executions
3. Configuration flags: store runtime flags that control iFlow behavior

Local Variables (Exchange Properties):
Exchange properties exist only during a single message processing run.
- Set via Content Modifier or Script
- Accessible throughout the iFlow execution
- NOT persisted — lost when processing completes
- NOT sent to external systems

Headers vs Properties vs Variables vs Data Store:

| Feature | Headers | Properties | Variables | Data Store |
|---------|---------|------------|-----------|------------|
| Scope | Single execution | Single execution | Across executions | Across executions |
| Persistence | No | No | Yes | Yes |
| External visibility | Yes (sent to adapters) | No (internal only) | No | No |
| Data size | Small (key-value) | Small (key-value) | Small (single value) | Large (full messages) |
| Cross-iFlow | No | No | Global visibility option | Global visibility option |
| Use case | Adapter config, metadata | Internal processing | State tracking | Message persistence |

Global vs Integration Flow Visibility:

Global:
- Accessible from any iFlow on the tenant
- Use for shared data (partner configs, global counters)
- Be careful with naming — avoid collisions

Integration Flow:
- Accessible only from the iFlow that created it
- Safer — no risk of cross-iFlow interference
- Use for iFlow-specific state

JMS Queues (for Async Processing):
JMS queues are another persistence mechanism, specifically for asynchronous message processing.
- Messages are stored in a queue until consumed
- Provides retry capability with configurable intervals
- Limited number of queues per tenant (based on license)
- Used for decoupling sender and receiver processing speeds

Best Practices:
1. Set appropriate retention thresholds on data store entries to prevent storage bloat.
2. Use Integration Flow visibility unless you specifically need cross-iFlow access.
3. Use meaningful data store and entry names for easier monitoring.
4. Use Variables for simple state (timestamps, counters) and Data Store for full messages.
5. Clean up data store entries after successful processing (Delete On Completion).
6. Monitor data store size regularly — each tenant has storage limits.
7. Use JMS queues for high-throughput async scenarios instead of data stores.
8. Consider data store entries as temporary — do not use as a long-term database.
